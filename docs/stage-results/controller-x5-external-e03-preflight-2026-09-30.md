# X5 external E03: HTTPX double-cancellation preflight

Date: 2026-09-30 Australia/Sydney. Status: **provider-free calibration complete;
rejected for blind paid X5**. No worker or Controller provider call occurred. The
machine record is `test/results/2026-09-30-controller-x5-external-e03-preflight.json`.

The original [HTTPX issue #3782](https://github.com/encode/httpx/issues/3782)
reports that cancelling a streaming task twice, with `await asyncio.sleep(0)`
between cancellations, can leave connections active until the pool is full.
The exact current issue body is frozen at
`test/fixtures/controller_x5_external/development/E03/source-issue.md`
(SHA-256 `ce3c81faa2f56068cde7695396bd35d73bb886cdfcc953ab5852b9d747e33262`).
It describes the symptom and a runnable client sequence without prescribing
a source repair. GitHub reports creation on 2026-02-26 and an update on
2026-09-23; the API update timestamp does not prove when, or whether, the
body was edited.

The issue uses a remote HTTP test service. The independent
[local-loopback adaptation](../../test/fixtures/controller_x5_external/development/E03/repro/repro.py)
retains its double-cancel sequence, `asyncio.sleep(0)`, nested async stream,
shielded close calls and pool-status observation, while serving HTTP/1.1
chunks from a local asyncio server. It uses a three-connection pool and a
three-second watchdog. This removes remote service timing and credentials,
but it is an adaptation rather than a byte-for-byte replay of the issue.
The pinned stack is HTTPX 0.28.1, HTTPcore 1.0.9, AnyIO 4.12.1 and h11
0.16.0. The installed `httpcore/_async/http11.py` SHA-256 is
`faa33d6d5ecf8d2405e6fc6cdfbf9e5173881706c88cf7196cd962b97f53b41c`.
The official HTTPcore 1.0.9 release points to signed commit
[`98209758cc14e1a5f966fe1dfdc1064b94055d8c`](https://github.com/encode/httpcore/commit/98209758cc14e1a5f966fe1dfdc1064b94055d8c);
the upstream repository declares BSD-3-Clause. The installed wheel's source

The observed active-connection growth and next-request timeout establish a
consequential failure on the worker host. They do not establish a Controller
uplift opportunity. A later, still-open
[HTTPcore proposal #1113](https://github.com/encode/httpcore/pull/1113),
opened on 2026-09-16, publishes a repair and tests. A historical task could

proposal, but model-memory contamination remains untested and must be

As a disposable provider-free positive control, the proposal's source-only

## Distinct retry probe and calibration limit

The pinned public source sets the byte stream's `_closed` flag before awaiting
connection cleanup; the latter can await network-stream close. A separate
[close-retry probe](../../test/fixtures/controller_x5_external/development/E03/repro/close_retry_probe.py)
injects one `OSError` at this connection boundary, then calls `aclose` again.
The probe tests retryability of this internal operation, not a demonstrated
real network error rate. A
[concurrent-close probe](../../test/fixtures/controller_x5_external/development/E03/repro/concurrent_close_probe.py)
checks that two successful close calls still reach the connection once.
The following disposable source variants were run with the unchanged local
issue reproduction and both probes on Windows and WSL:

| Source | Double-cancel pool | Retry reaches connection | Concurrent close once |
| --- | --- | --- | --- |
| Pinned 1.0.9 | Exhausts pool | No | Yes |
| Cancellation-only repair | Clear | No | Yes |
| Published #1113 source repair | Clear | Yes | Yes |
| Separate serialised-close repair | Clear | Yes | Yes |

The cancellation-only variant is generated by
[`make_cancel_only_variant.py`](../../test/fixtures/controller_x5_external/development/E03/repro/make_cancel_only_variant.py)
and has source SHA-256 `c0c875c149f7b5e432ccd0bfc2e6c33a4bd8db8044900891c6728e9f94ee8c18`.
The serialised-close variant is generated by
[`make_serialised_close_variant.py`](../../test/fixtures/controller_x5_external/development/E03/repro/make_serialised_close_variant.py)
and has source SHA-256 `c568b704e75a7056f30966ce005155af80cc48433e1359a3ff3e98d535b85fe9`.
These are local calibration controls, not independently accepted upstream
repairs. The source-only published patch also changes the synchronous sibling;
the separate serialised variant does not. No full upstream suite was run on
either local variant.

The [later public PR #1113](https://github.com/encode/httpcore/pull/1113)
already publishes the `_closed` diagnosis, retry-failed-close tests and the
repair. Our retry probe is separately written but its acceptance idea is not
independent of that published work. A retrospective paid task could reward
model memory or a narrow solution copied from it. The exact February issue
body history remains unverified. Thus E03 is **not admitted** as a blind X5
quality comparison, despite the deterministic failure and calibrated gap.
There is no frozen actor package, protected oracle, prospective sample plan,
dated paid notice or matched S/A root. Do not dispatch a paid E03 producer.

# X5 six-task pilot predeclaration

Date: 2026-09-28 Australia/Sydney. Status: **design frozen before pilot
provider calls**. The X4 runtime and X3 development corpus are the input.
B0 remains the shipping default. This document does not claim that any task
will actually trigger the Controller.

## Task screen

The four proposed Controller-suitable tasks are chosen from public issue
text only. C01-D1 challenges a queue-reorder diagnosis with alias evidence
and strict account boundaries. C03-D2 challenges a duplicate-delivery
diagnosis with a lease/fencing race. C06-D1 challenges a database-saturation
diagnosis with clock-skew evidence. C07-D1 has conflicting financial totals
across two consumers and a consequential rounding rule. These are hypotheses
about the value of checking premises and cross-component constraints, not
labels supplied to the assessor or Controller.

N01-D1 is the ordinary rename control. C08-D2 is the missing-decision control:
the requested response field conflicts with a published version-one
contract. It should produce a focused clarification without a speculative
code edit. The task IDs are fixed for this pilot; choosing replacements after
seeing provider output would require a new dated screen and would be reported
as development tuning.

## Arms, order and isolation

Each task receives B, S and A in a precommitted rotating order, with a fresh
actor and N1 root for every episode. B is frozen B0 worker-only. S is the
qualified N3 worker policy without Controller. A uses that same worker policy
and the `auto` Controller decision. Neither actor nor live model can read
protected oracles, other arms' work or the intended suitability label. Public
assessment and role calls use WSL Claude Code with Claude.ai authentication,
not an API key. The N1 budget ledger records every started, failed, blocked
and uncertain call. A root is never replayed after an uncertain charge.

Before worker or Controller calls, run the six A-arm public assessments and
freeze their actual interpretations, decisions, requested cells and costs.
Stop the pilot if fewer than four of the four predeclared suitable tasks
receive an automatic Controller decision, if the ordinary control receives
one, or if the missing-decision control is not a clarification. Diagnose and
record the failure before any policy revision or further paid campaign.
No explicit `on` override may be used to satisfy the four-admission gate.

If the screen passes, complete the 18 B/S/A episodes. Exercise one explicitly
labelled frontier role profile on a suitable A task within its allowance;
keep its suitability evidence separate from the standard profile. Require at
least one independently verified Controller-to-worker completion, complete
gap/failed-attempt accounting and the real clarification result. A role call
or visible public pass alone earns no acceptance credit.

## Measures and stop rules

The protected grader records acceptance, quality on a 0-100 scale, semantic
outcome including useful partial work, safety errors and verified causal
probes. Report per-task paired A-S and B-S differences, with completion and
quality separate. Record served model, requested effort, Controller role,
selected worker cell, actual automatic admission, total and component cost,
latency, budget holds and censoring. Shared preparation cost is reported
once in actual spend and both fully and amortised in arm comparisons.

The campaign allocation ceiling is **18 episodes x USD 8 = USD 144**,
including up to USD 4 Controller, USD 3 worker and USD 1 assessment and
verification per episode. A screening-only stop spends at most six public
assessment allowances and no role/worker allowances. These are local
admission limits, not an invoice guarantee. Current X4 receipts suggest a
much smaller API-equivalent total, but the X5 estimate remains **USD 5-30**
with low confidence until a bounded runner and host preflight are validated.
Allow **3-8 hours** for the paid pilot plus engineering and operator waits.
The exact dated spend notice, manifest digest and host identity must be
recorded before the first pilot call. No X6 default-promotion claim follows
from this development pilot.

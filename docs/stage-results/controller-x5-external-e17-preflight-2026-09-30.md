The frozen natural [Pydantic #13754](https://github.com/pydantic/pydantic/issues/13754) report says that, with `serialize_by_alias=False`, `model_dump()` emits field names but `model_json_schema(mode="serialization")` emits serialization aliases. The exact issue body is stored in `test/fixtures/controller_x5_external/development/E17/source-issue.md` with SHA-256 `1d5149e98fb11b155f357cfae3f75ec2e7265ce4bd7aa25346b2059cca8a14e5`. It names related alias-consistency issues but provides no linked repair patch.

The local reproduction pinned Pydantic 2.14.0b1 and pydantic-core 2.48.0 in disposable packages. The same script passed on Windows and the WSL worker host. For the default model, `model_dump()` produced `my_field, computed`; the default serialization schema produced `myAlias, computedAlias`. With `model_json_schema(mode="serialization", by_alias=False)`, the schema instead produced `my_field, computed`. For a model configured `serialize_by_alias=True`, the dump and default schema both produced alias keys; explicitly selecting schema `by_alias=False` still produced field names. The structured observations are in `test/results/2026-09-30-controller-x5-external-e17-preflight.json`.

The pinned method signatures expose independent switches: `model_json_schema(by_alias: bool = True, ..., mode="validation")` and `model_dump(..., by_alias: bool | None = None, ...)`. The report's mismatch is real for the two default calls, but a caller can already request either schema key convention. Changing the schema default or making it follow `serialize_by_alias` would change the existing API contract. Whether that compatibility change is desirable remains a maintainer policy question, not a settled independent repair oracle. A worker could satisfy the reported example by changing the default and break callers that rely on `by_alias=True`.

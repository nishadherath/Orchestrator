### What I believe the system is

A cost-routing layer for Claude Code subagents, delivered as configuration
and prose rather than application code. Fifteen worker definitions
(`.claude/agents/WORKER_{sonnet,opus,fable}_{low..max}.md`) give a consumer
project a grid of three models by five effort levels. A top-level session,
the orchestrator, reads `ORCHESTRATOR.md` (an assembled copy of
`src/ROUTING.md` plus `src/LIFECYCLE.md`) and, for every task it would
delegate, states a one-line assessment on three axes (intelligence
sensitivity, horizon, blast radius) plus two flags, then runs
`python3 tools/route.py --from-line ... --explain`, which resolves that
line to a cell deterministically from `src/routing_table.json`, Bayesian
priors in `src/routing_priors.json`, and the consumer project's own
`.claude/routing-ledger.jsonl`. The split is deliberate: the model judges
on a rubric with the destinations hidden from it, because a model that can
see the destinations bends its assessment toward the one it prefers.

### What it does for a consumer

Every task starts at the cheapest cell, `worker-sonnet-low`, and climbs
the ladder only on a recorded failure; the ledger makes the priors move
per project over time. Two triggers can send a task to a separate Python
program, the Controller (`tools/system_controller.py`), a multi-role
`claude -p` state machine costing a few US dollars per fire: a proactive
policy or expected-cost rule resolved by `route.py`, and a reactive one
when a worker reports a task constraint whose stated justification the
repository shows to be false. After each task the orchestrator records
the outcome with `route.py --record`. Handoff files under `handoffs/`,
written with `tools/handoff.py`, carry state across a model or effort
change of the orchestrator's own session; a `SessionStart` hook runs
`route.py --recover` after a platform compaction. A context probe wired
into the status line lets `--explain` warn when the orchestrator's own
context is near the compaction threshold, and an overflow advisory tells
it to split a task into sub-handovers rather than let a worker compact.

### How it is used

Copy `dist/.claude/`, `dist/ORCHESTRATOR.md`, `dist/preflight.py`,
`dist/tools/*.py`, `dist/src/*.json` and `dist/src/System/` into the
consumer project in the same relative layout, create `handoffs/`, merge
`settings.fragment.json` into `.claude/settings.json`, add the pointer
line and the Handoffs section to `CLAUDE.md`, run `preflight.py`, restart
Claude Code if `.claude/agents/` is new, then verify with `/workers`, a
`/tasks` row on a small spawned task, and the presence of the routing
line in the orchestrator's narration. Seven settings silently defeat it,
listed in the README's table; the worst are the three environment
variables that flatten model or effort, and agent teams.

**A4** (defect, `tools/route.py:479`). The floor's posterior only counts a
failure when the entry has at least one escalation. A `--record --outcome
fail` with no `--escalation` flag (the worker failed and the orchestrator
gave up or did the task itself) moves nothing, so a bucket where the floor
keeps failing without anyone climbing never learns. `--outcome fail` is a
legal record per the CLI and per `ORCHESTRATOR.md` section 2, so the
mechanism silently ignores the most direct evidence it is designed to
collect. Fix: count `final_outcome == "fail"` at the floor as a floor
failure whether or not an escalation was recorded, and say so in
`posterior()`'s docstring; add a selftest scenario. Size S.

money except `system_controller.py`, which is gated only by

## Pass 4, synthesis

### Grading the cold read

The pass 0 paragraph got the mechanism right and the economics wrong,
and the gap is the documentation's, not the reader's.

Right, from the five files alone: the assessment line, `route.py`
resolving it from priors plus a per-project ledger, spawn by
`subagent_type` only, `--record` after the task, the ladder, the two
Controller triggers, handoffs, the context probe and the overflow
advisory, the seven settings that defeat it, and the install sequence.

Wrong or missing, and what corrected it:

- The cold read absorbed "defaulting to the cheapest and escalating only
  on evidence" as a design choice. The measured fact is stronger and
  appears in none of the five files: ten of eleven benchmark tasks
  cleared at `worker-sonnet-low` at the reporting bar, and the one that
  did not failed on disposition, not capability (D42, `docs/FRONTIERS.md`).
  A newcomer should learn that before learning the rubric.
- It absorbed "cost-routing layer" as a claim of savings. The premise
  ledger's dissolution check shows a routing verdict costs about as much
  as the floor run it routes (ratio 1.003 pre-E27, 1.40 after), so the
  honest product claim is insurance against an undetected wrong answer,
  not money saved (`docs/PREMISES.md`, `docs/COST.md`). None of the five
  files says this; `dist/README.md` never mentions cost per verdict.
- It believed compaction recovery lists pending workers. It cannot,
  because nothing shipped ever writes one (B1).
- It believed `/workers` confirms the install (B7) and that the
  orchestrator can read `/tasks` (B6). Neither holds (E19).
- It believed the ledger learns from every recorded failure. It learns
